# CivicPulse: Detailed Phases 1 to 5 Summary (Demo Preparation)

This document provides a detailed breakdown of the first five phases of the CivicPulse project. Use this as your master reference guide to explain the architecture, technologies used, and engineering decisions during your assignment demo.

---

## Phase 1: Frontend Shell (React + Vite)
**Goal:** Build the visual shell of the application without a real backend.
* **What we did:** We created the initial React frontend with three main pages: Submit a Complaint, Dashboard, and Stats. We set up routing using `react-router-dom`, established global CSS styles, and created strict TypeScript interfaces for our data models.
* **Technical Details:** 
  * We used `Vite` as our build tool because it is significantly faster than Create React App, offering instant server starts and lightning-fast Hot Module Replacement (HMR).
  * We built reusable React components (like a `Navbar` and a `ComplaintCard`) to keep the codebase DRY (Don't Repeat Yourself).
  * Since we had no backend yet, we created a `sampleData.ts` file containing hardcoded JSON data. We injected this directly into our React state so we could visualize what the Dashboard would look like when populated.

## Phase 2: Backend API Shell (FastAPI)
**Goal:** Build the backend API endpoints and strict business logic, utilizing a temporary in-memory data store.
* **What we did:** We created a Python backend using the FastAPI framework. We defined RESTful API routes (`POST /api/v1/complaints`, `GET /api/v1/complaints`, etc.) and implemented a strict status-transition rule engine (e.g., Open -> In Progress -> Resolved).
* **Technical Details:**
  * **Validation:** We used `Pydantic v2` to create input schemas (`ComplaintCreate`) and output schemas (`ComplaintOut`). This guarantees that any data entering or leaving our API is perfectly typed and formatted.
  * **Business Logic:** We strictly enforced state machine transitions in the service layer. If a user tried an illegal move (like moving a complaint from "Resolved" back to "Open"), the API returns a precise `409 Conflict` HTTP error.
  * **Storage:** We temporarily stored data in a Python dictionary (`complaint_repo.py`) to test our API endpoints instantly via the autogenerated Swagger UI (`/docs`), allowing frontend development to proceed without waiting for a database setup.

## Phase 3: Frontend-Backend Integration
**Goal:** Connect the React frontend to the FastAPI backend over the network.
* **What we did:** We replaced the hardcoded sample data in the frontend with real HTTP network requests to our FastAPI server.
* **Technical Details:**
  * **CORS:** We configured Cross-Origin Resource Sharing (CORS) in FastAPI to securely allow the frontend (running on port 5173) to communicate with the backend (running on port 8000).
  * **Data Fetching:** We used React's `useEffect` hook to fetch complaints when the Dashboard loads. 
  * **Error Handling:** We wired up the frontend UI to catch backend HTTP errors. Specifically, if the backend returned a `409 Conflict` during a status update, the React frontend catches that exception and renders the exact error message verbatim to the user.

## Phase 4: PostgreSQL Persistence (Database)
**Goal:** Replace the temporary in-memory dictionary with a real, permanent, relational database.
* **What we did:** We connected our backend to a PostgreSQL 16 database so that user complaints persist across server restarts.
* **Technical Details:** 
  * **Dockerized Database:** We ran PostgreSQL inside a Docker container (`docker run postgres:16`). This ensures a clean, isolated local development environment without the mess of installing Postgres manually on our host operating systems.
  * **SQLAlchemy (ORM):** We used SQLAlchemy to map our Python classes directly to database tables. This Object-Relational Mapping (ORM) allowed us to perform CRUD operations using Python code rather than raw SQL strings.
  * **Alembic (Migrations):** We introduced Alembic to manage database schema changes. We ran `alembic revision --autogenerate` to automatically detect our SQLAlchemy models and generate a migration script, and `alembic upgrade head` to safely build the tables in Postgres.

## Phase 5: AI Triage & Rule-Based Fallback
**Goal:** Use an LLM (Large Language Model) to automatically triage incoming complaints, while ensuring 100% reliability if the AI goes down.
* **What we did:** We integrated the Groq API to analyze the text of newly submitted complaints. The AI automatically assigns a Priority (High/Normal/Low) and writes a concise summary of the issue.
* **Technical Details:**
  * **Groq API Integration:** We used the `llama-3.1-8b-instant` model via the Groq provider to read the complaint description and output structured JSON containing the `priority` and `ai_summary`.
  * **Database Migration:** We created a new Alembic migration to add the triage columns (`priority`, `ai_summary`, `triaged_by`, etc.) to our existing `complaints` Postgres table safely without losing data.
  * **Robust Fallback Engine:** The most important engineering decision was the fallback strategy. If the Groq API times out, crashes, or returns invalid JSON, our backend catches the exception and immediately routes the complaint to a local `rules.py` engine. This rule engine scans the text for keywords (e.g., "fire", "leak") to assign priority instantly. This guarantees that the user *always* receives a `201 Created` success message, fulfilling our requirement that the system never breaks.

---
**Current Status:** The application has a React frontend, a FastAPI backend, a permanent PostgreSQL database managed by Alembic, and an AI-powered triage system with a zero-downtime fallback mechanism.
